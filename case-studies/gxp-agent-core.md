# gxp-agent-core

**A regulation-driven context framework that makes a coding agent produce
inspection-ready pharmaceutical software by default.**

`Claude Code · Python · YAML · Markdown`

---

## The problem

Ask a coding agent to build a system for a GMP manufacturing client and it will
build you a working system. It will not build you a compliant one, because
compliance in this domain isn't a feature you bolt on — it's a set of structural
constraints that have to be true from the first migration.

An audit trail, for instance, isn't "log the changes". It's: the entry is
written inside the same database transaction as the change; the user ID comes
from the server-side session and never from the request payload; the timestamp
is generated by the database at INSERT and cannot be overridden by the
application; no role — including administrator — holds UPDATE or DELETE on that
table; a change reason is non-blank and enforced at the API boundary.

Get that wrong and you don't find out during development. You find out during an
inspection, and the remediation is a rebuild.

The domain knowledge to get it right exists — it's in 21 CFR Part 11, EU GMP
Annex 11, ALCOA+, GAMP 5 and half a dozen others. It just isn't in a form an
agent can act on.

## What I built

Three layers, deliberately kept orthogonal.

**Regulatory knowledge** (`regulatory/`) — one file per regulation, containing
only the software-relevant clauses: 21 CFR Part 11, EU GMP Annex 11, ALCOA+, EU
GMP batch records, ATMP Regulation 1394/2007, ICH E6 GCP, EU GMP Annex 1, GAMP 5
CSA.

**Implementation patterns** (`patterns/`) — one file per GxP control: audit
trail, electronic signatures, RBAC, data integrity, no-delete archiving, chain
of identity, batch release, environmental monitoring. Each carries structured
frontmatter with its regulatory basis, an `applies_when` condition, and a list
of **acceptance criteria written as testable statements**. Those criteria are
the direct input to an OQ test script — the same sentence that tells the agent
what to build tells the validation package what to test.

**Scope resolution** (`compliance/`) — profiles bundle regulations for known
client contexts (`gmp-manufacturing`, `atmp-clinical` and others). A client
declares a profile; a resolver expands it to the exact control set that client
needs. Nobody hand-picks controls, so nobody forgets one.

## Two modes from one model

The same resolved control set drives both directions:

- **Build mode** — build to each pattern's acceptance criteria, and emit a
  validation package appropriate to the component's GAMP category.
- **Assess mode** — take an existing system and diff it against the same
  criteria, producing a gap report of PASS / FAIL / UNVERIFIABLE findings with
  risk-graded remediation.

Assessment was not the original goal. It fell out of having written the criteria
as testable statements rather than as guidance, and it's the more commercially
useful of the two.

## The bit I'm most pleased with

**The architecture is machine-checkable.** `tooling/consistency-check.py` runs
before any build or assessment and must exit clean. It catches:

- a regulation referenced anywhere that doesn't exist in `regulatory/`
- a pattern whose regulations appear in no profile or product context — an
  orphan nobody can ever reach
- a profile carrying a field it shouldn't (GAMP category belongs on components,
  not profiles — mixing those two axes is the most common way this kind of
  model rots)
- a context whose scope resolves to nothing

A second script tests the resolver itself against known inputs.

This matters more than it sounds. A context framework for an agent is only
useful if it stays internally consistent as it grows, and prose conventions
don't survive contact with a deadline. Encoding the invariants as a failing exit
code does.

## Shape of it

- **47 markdown files** across regulations, patterns, schemas, contexts and
  validation templates.
- **8 regulations**, **9 implementation patterns**, composable profiles.
- Full URS / FS / IQ / OQ / PQ / VSR validation templates.
- Schema files defining the authoring format for every file type, so the
  framework can be extended without drifting.
- A user manual and an SOP, because the intended user is a consultant on an
  engagement, not the author.

## Why it's here

This is the project that best describes how I think about deploying AI into a
regulated industry. The model isn't the hard part. The hard part is getting
twenty years of domain knowledge into a shape the model can act on reliably,
and then proving it's still consistent six months later.
